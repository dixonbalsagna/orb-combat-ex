# Warming the ground's nodes at the match start (World, 2026-11-02)

Rendering, through the EP: after `water-read`, the tile bake's ground point is 62 microseconds, and 32 to 40 of them are the node read (`WorldField.ensure`): the first visit to a node pays the planet's own function. A warm-up of the nodes round the start would take it out of play. **Parked, off by default:** `docs/world/pending/node-warm/`.

**What it is.** `WorldField.warmNear(F, point, radius, budget, state)` reads every canonical node within `radius` units of a point (a face's lattice carries on past its edge, so the disc may cross onto the next face), a slice at a time if asked (`budget` nodes a call; `state` is the caller's progress), and the match start calls it for the touch-down with `field.json` `warm.radius` (0 is off). Nodes are the field's own (`ensure`): the same read an on-demand visit does, so a later view finds them.

**Hash-safe.** A node is a pure function of the seed and the data, so which nodes are loaded never changes a result (the field's rule: a reader's level is fixed by the reader, never by what is loaded). `NODEWARM` 0 failed: off in the data as shipped; a radius of 4,000 reads 2,694 nodes, a second call reads none; a slice at a time it ends; 40 sampled warmed nodes equal a fresh read bit for bit; a 17 by 17 block read in the disc reads nothing new; and **a match with `warm.radius` 8,000 has the same state hash as one without**.

**What it costs at load** (native, this PC, a loaded machine, planet 13 cold with the cache off; `newMatch` takes 2.2 s with it off):

| `warm.radius` | nodes read in all | extra nodes | `newMatch` | extra |
| ---: | ---: | ---: | ---: | ---: |
| 0 (off) | 19,456 | 0 | 2.1 to 2.3 s | 0 |
| 8,000 | 28,529 | 9,073 | 2.63 s | +0.34 s |
| **10,000 (the data)** | 34,170 | 14,714 | 2.9 to 3.2 s | **+0.5 s** (0.5 to 0.9 on a loaded PC) |
| 16,000 | 60,272 | 40,816 | 4.14 s | +1.9 s |

About 40 to 50 microseconds a cold node, 6 bytes a node. A repeat match on the same planet pays nothing (the nodes are in the field's memory, and in the pool on disk with `cache.pool`). On the web the same read is slower (the sim's ground reads were about 2.4 times the native cost in the earlier estimate; not measured for this). **The radius is 10,000, Rendering's number (the tile bake reads to about 9,600 at load).

**To hide it behind the loading screen** (instead of 0.34 s inside `newMatch`): `SimPlanetLoad` (Simulation's) would call `warmNear` in its own phase, a slice a step with `budget`, as it does the bake; the function is built for that (it keeps its place in `state`), one phase and its progress units (a node is `NODE_UNITS` of 2) are Simulation's change. Not built.

## The follow-camera warm: a plan (not built; the EP's ask, 2026-11-02)

**What Rendering reads in play** (their read): every node to about 15,000 units and every second node to about 20,000 around the camera, wherever the fight moves. The load warm above covers the start (to 10,000); nothing covers the camera once it moves.

**The size of it.** Every node to 15,000 is about 43,000 nodes, every second node from 15,000 to 20,000 another 13,000: 56,000 nodes, about 2.7 s of reads at 49 microseconds, about 3.4 MB if the whole disc were new (a node is 6 bytes). A budget of 1 millisecond a frame is 20 nodes: a still camera is warm in under a minute. **The camera moves, and that is the catch:** at the base flat-out speed (5,000 a second, 83 units a frame) the disc's leading edge brings about 150 new nodes into the disc every frame, 7 to 8 times a 1 ms budget; at the maximum (190 a frame) about 350. **A slow warm cannot keep ahead of fast flight.** It helps when the camera is still or slow (a fight in one place, a landing), and after a fast flight ends it fills what the flight left; at speed the view's own on-demand reads stay what they are. Two levers beyond the slow warm: **lead the disc** (read the leading edge first, by the camera's velocity), and **read ahead of a known destination** (a launch's predicted landing, a swing's end: sim-side knowledge, Encounter's, and a pure read like this one).

**The call.** World owns the function and its data: `WorldField.warmView(F, state, qx, qy, qz, vx, vy, vz, budget)` (the same engine as `warmNear`, ordered by distance from the current point with the leading edge first, re-centred when the point has moved more than a threshold, two densities: every node to `warm.follow.full`, every second to `warm.follow.half`; `budget` nodes a call). **Rendering owns when and how much:** it calls it once a frame after the sim's step, with a node budget from its own spare time (the last frame under its target), and gives it the camera's point and velocity. **Not from the sim:** the sim must not depend on frame time or the camera, and nothing in `SimCore.step` would call it.

**Is it within "rendering never writes sim state"?** Yes, and for a reason the tile bake already relies on: **the nodes are a cache, not sim state.** They are not in the state hash, not in a snapshot (`NetSnapshot`), and not in a replay; the sim reads a node through `ensure`, which computes it from the planet's pure function if it is not there, so a hit and a miss give the same bits. `F.h`, `F.b`, `F.f` are derived data like `SimField`'s memos and the bake. **Rendering already fills this cache today:** the tile bake's ground point is `WorldField.ensure` (the 32 to 40 microseconds), so a view call that fills it earlier and in a budget adds no new kind of write, only a different time. What the rule needs us to prove is "never a sim input", and that is what the checks do: `NODEWARM` shows a match with the warm is the same match (state hash); the follow-warm would add a check that interleaves `warmView` calls from a wandering camera with `SimCore.step` for a match and for Orb's replay and compares every checkpoint and the final hash.

**Things to settle with Simulation** (through the EP): (1) that a view-driven `ensure` between ticks is accepted under their rule for the reason above (it is the call the tile bake makes now); (2) **not during a step**: `ensure` and the planet function use shared statics (`_vh`, `_vb`, `_vf`), so a warm call must never run inside a sim step or a sim read; once a frame, after the step, on the main thread, is safe; (3) `F.extra` (the pool candidates, kept to be written to disk at a load's end) fills to its cap of 60,000 as nodes are read: view-warmed nodes should not join it (a flag on `ensure`, or reading by a path that does not append), or the cap fills with camera nodes and the disk pool stops keeping the ring's nodes of later matches; that is only a cache, never a result; (4) on the web the planet function is slower (2 to 3 times), so the budget in nodes is smaller there: Rendering's spare-time budget handles it if it counts nodes by time, not by number.

**What I would build when told:** `warmView` and its data (`warm.follow`), the `ensure` flag for (3), `NODEWARMFOLLOW` (the order, the two densities, the re-centre, the budget, the hash proof with a wandering camera), and the replay proof on Orb's matches; no sim file changes. Estimate: about one working window.
