# Alpha audit, area ENERGY: energy, stamina and health

Baseline 8901d351 (game code as in the last played build, 6a30b4c9). Read-only. Every line cites a file on disk now, a CI run, a saved record or a build's own data. "Ki" is the code's name for a fighter's energy; "wear" is the code's name for injury to one of four body parts (head, core, arms, legs); the "brink" is the state where a fighter can be finished; the "ladder" is the power number (0 to 100) whose thresholds make a transformation ready.

## Summary

- **Works:** health is already bar-free and injury-based (four body parts with stages, only a finisher ends a match), it shows on the fighter (marks, posture, aura flicker), and a third fighter made of data alone plays a match in CI.
- **Does not work:** there is no stamina and no "body" number anywhere in code or data; energy's numbers (start, cap, regain, every cost) are written in code, shared by all fighters; the "one energy model" is off in data and switched on in Orb's build by a code patch the page tool writes.
- **Biggest gap:** Orb's Alpha asks for "a working energy, stamina and health system" and answered a plan for it on 2026-11-13; none of that plan is designed to a build page or built, and it changes the state hash, the knockout rule and the HUD.
- The backburnered hero and villain meters still change damage, energy regain, beam contests and the computer's choice of ground in every match, unseen.
- X-15 is not met: no single page, energy numbers not in data, and the named tool (the two-fighter ratchet) measures something else.

## Questions and answers

**Q1. What exists today: ki or charge, the Wounds damage model, the power model, stamina if any.**

- **Energy (ki).** One number per fighter, 0 to 100, starting at 60 (`sim/core/state.gd:1077`). It regains 5 a second while free (`sim/core/fighter.gd:685`, `:711`), 30 a second while charging (`sim/core/fighter.gd:767`), is gained on landing a hit and lost on guarding one (`sim/core/damage.gd:89-90`). Costs are literals in the director: heavy 4, signature 45, chain link 6, clash answer 40 (`sim/director/exchange.gd:294`, `:343`, `:348`, `:595`; `sim/director/beam.gd:101`, `:134`, `:140`). Newer moves (stick beam stages, shots, brake) keep costs in shared data files (`data/director/stick.json`, `data/fight/shots.json`, `data/fight/brake.json`; listed by grep, not read in depth).
- **Health (Wounds).** Built and live. Four regions with fixed-point wear and four stages (`sim/core/wounds.gd:19-31`); the old hit-point number no longer ends a match (`sim/core/wounds.gd:38`, `sim/core/damage.gd:25-26`, `:41`); the brink is the core's wear (`sim/core/wounds.gd:236-241`); wear recovers (`sim/core/wounds.gd:171`). Numbers are in `data/fight/wounds.json` (for example `:29` wear per damage, `:95` energy regain with a battered core), shared by every fighter, with an optional per-fighter file (`sim/core/fighter_data.gd:160-190`). The hit-point number is still tracked as a readout (`sim/core/damage.gd:25-26`, `sim/core/roster.gd:29`).
- **The power ladder.** Power fills with time, charging and damage dealt or taken; thresholds 35, 65, 100 make a transformation ready (`data/fight/ladder.json:4-13`; `sim/core/fighter.gd:661-678`; `sim/core/damage.gd:91-92` region). Orb's build charges at 2 a second, main at 0.5 (`homework/Files/builds/orb-first-play-6a30b4c9-6627cb9d/tree/data/fight/ladder.json:5`; `data/fight/ladder.json:5`).
- **The "one energy model"** (how hard a blow sends a body, by tier and power: `sim/core/power.gd:3-5`, `data/fight/power.json:5-8`). Off in data on main (`data/fight/power.json:4`) and off in both played builds' own data (`.../orb-first-play-6a30b4c9-6627cb9d/tree/data/fight/power.json:4`, `.../orb-lan-6a30b4c9/tree/data/fight/power.json:4`). In Orb's build it is on because the page tool patches the host code to pass "power" in the match setup "whatever the data says" (`tools/preview/switches.mjs:918-919`; the build's page still honours `?power=0`, `.../orb-first-play-6a30b4c9-6627cb9d/web/index.html:149`). The specification's note "switched on by the page, not by data" is confirmed.
- **Forms (the Protagonist's own five steps).** Off in data on main and in both builds (`data/fight/forms.json:4`; build trees `data/fight/forms.json:4`). Both fighters transform on the shared four-tier ladder (RR-02, spot-checked: `sim/core/fighter.gd:661-678`).
- **Stamina.** None. `git grep -i stamina 8901d351 -- sim render ui net data audio` returns nothing. It exists only as Orb's words (`docs/ep/vision.md:1735`, `:1756`, `:1787-1788`) and two plan pages (`docs/ep/proposals/alpha-feature-workshop.html`, `docs/ep/proposals/alpha-feature-workshop-2.html:42-50`, `:133-148`).
- **"Body"** (the deeper number in Orb's answered plan): none in code; `docs/ep/proposals/alpha-feature-workshop-2.html:72-78` is a plan, and Orb's answer is "workshop this" (`docs/ep/vision.md:1786`).

**Q2. Is there one written model? Does each number live in data per fighter?**

- **One page: no.** The model is spread over `docs/design/damage-model.md` (still headed "proposal for Orb to react to", 2026-09-29, `:3`; it says the brink is "core breaks, or any two regions break", `:24`, where the code uses the core alone, `sim/core/wounds.gd:13`, `:236-241`), `docs/design/spec-wounds.md` (uncommitted changes at the baseline), `docs/design/power-scale.md`, `docs/design/energy-overhaul.md:182-190` (energy costs "as first values"), `docs/design/minimal-hud.md` and `docs/design/balance-targets.md`. None mentions stamina (grep of `docs/design/*.md`: two hits, both in `melee-press-feel.md`).
- **Numbers in data per fighter: partly.** In data and per fighter: damage multiplier, speed, the old hit-point maximum (`data/fighters/PROTAGONIST/fighter.json:10`, `data/fighters/RIVAL/fighter.json:10`), the backburnered meters (`data/fighters/*/meters.json`). In data but shared, with a per-fighter override the loader supports: wounds and ladder (`sim/core/fighter_data.gd:160-190`). **In code, shared, no data:** energy's start, cap, regain, charge rate, hit gain, guard drain and the old costs (lines under Q1); the stance damage table, combo growth and the charging penalty (`sim/core/damage.gd:5`, `:58`, `:84`); five pinned wound constants other files read (`sim/core/wounds.gd:32`, `:36`, `:44-46`).

**Q3. Does it suit high-speed combat: can a player read their own state without looking away, with nothing drawn over the fighters?**

- **Nothing over the fighters: met in the normal HUD.** With `minimal_hud` on (`ui/data/features.json:15`) the damage arcs around the body ("crown"), the beat ring, the struggle and tug gauges are not drawn (`ui/hud/ui_hud.gd:771`, `:778`, `:852`, `:891`).
- **Health reads from the fighter:** marks on the body by region and stage (`render/core/fighter_view.gd:266-284`), a sag in the stance and slower get-ups toward the brink (`render/anim/anim_fighter.gd:5277-5281`, `:2852-2854`, `:2900`), an aura flicker from a battered core (`render/vfx/react.gd:84-89`).
- **Energy does not read from the fighter:** the only energy readout found is the bar on the corner plate (`ui/widgets/ui_plate.gd:105`, `:473`); a charge shows as aura per the design (`docs/design/minimal-hud.md:22`) but no low-energy cue on the fighter was found. Not evidenced either way beyond that.
- **Whether a player can in fact read it at speed: not evidenced.** No saved record of a read test was found.

**Q4. No health bars; health shown on the fighters. What's built, what does the HUD show, what must change?**

- **Built:** the UI plate has no health bar by design (`ui/widgets/ui_plate.gd:3`); in minimal mode it keeps the name, energy and the power pips, and drops the stance chip, state chips and the ego meter (`ui/widgets/ui_plate.gd:105`). Wound cards (one line such as "ARMS: BROKEN") sit in the outer column, never over the fighters (`ui/widgets/ui_cards.gd:2-4`). The body figure beside the plate is off by default (`ui/hud/ui_hud.gd:52`). Damage counts move to the pause and result screens (`ui/hud/ui_hud.gd:794-795`).
- **Still a health bar:** the old greybox overlay draws a hit-point bar, an energy bar, a power bar and a MENACE or ANGUISH bar (`render/core/hud.gd:219-222`, `:228-233`), and F2 swaps it in on the shipped scene (`render/core/main.gd:117`, `:1547`).
- **What must change so state reads from the fighter:** (a) body marks only ever grow to the worst stage reached and never fade (`render/core/fighter_view.gd:266-271`), while wear recovers and Orb wants a new form to ease injuries (`docs/ep/vision.md:1784`), so the body cannot show getting better; (b) energy and (once built) stamina have no on-fighter read; (c) the power pip is computed with 25 per tier (`ui/core/ui_sim_bridge.gd:86-87`) while the thresholds are 35, 65, 100 (`data/fight/ladder.json:10`), so the pip reads full before a form is ready; (d) the F2 overlay.

**Q6. What would adding a third fighter need? The two-fighter ratchet's own report.**

- **The ratchet's report (run read-only, `node tools/ratchet-two-fighter.mjs --list`):** "now 365, baseline 365; by spelling S.dirS.ex 153, fighters[0] 83, fighters[1] 57, SimRoster.opp 72"; "two-fighter ratchet ok: 365 against a baseline of 365". The stored baseline agrees (`tools/ratchet-two-fighter.json:10-16`). It runs in CI (`.github/workflows/ci.yml:88-91`); CI on the played build's commit passed (run 42722446938); CI on the baseline commit was still running when read (run 43554356718).
- **What it measures:** places where shipped code names exactly two fighters, for the two-against-two restructure (`tools/ratchet-two-fighter.mjs:1`, `:8`). It does not look for code written for one particular fighter. It is the wrong proof for "a third fighter needs data and art only".
- **The real evidence for the sim:** the roster already holds a third, data-only fighter (`data/fighters/roster.json`; `data/fighters/REFERENCE/fighter.json`), and the parity gate copies the Protagonist's files to a new id and plays a match "no code change" (`sim/core/tools/parity.gd:4162`, `:4193`; in CI at `.github/workflows/ci.yml:191`).
- **What a third fighter needs today:** a folder with `fighter.json` (and meters, wounds, ladder only where he differs: `docs/architecture/fighters-as-data.md:32`); rows keyed by his id in shared content files, for example `data/combat/finishers.json:7`, `data/director/alchemy.json:7-8`, `data/anim/fighters.json:6`, `data/anim/stick_pre.json:9-10`, `data/fight/power.json:91-102` (keyed by a lower-case name, not the roster id); names in `ui/data/fighter_names.json`; a readout profile (`ui/data/readout_profiles.json:41-43`).
- **Code that is still fighter- or role-specific:** the outfit table by roster id (`render/core/look.gd:489`, with a default at `:490`), a visor list by id (`render/vfx/glare.gd:23`), hair and gear chosen by "hero" or "villain" (`render/core/fighter_view.gd:124`, `:137`, `:220`), the role list in the loader (`sim/core/fighter_data.gd:399`), the meter list fixed to two names (`sim/core/fighter_data.gd:20-23`), and "the Protagonist's five steps" for forms (`sim/core/state.gd:95`; the rival has no `forms.json`).
- **A new kind of meter (stamina) is not data-only:** the loader accepts only the two backburnered meters (`sim/core/fighter_data.gd:20-23`).

## Decisions for Orb

1. **How much of the stamina, energy and body loop must be in Alpha?** Recommendation: the whole loop you described, built as shared rules with each fighter's numbers in their own data, switched on only after QA has measured how often the fighter who falls behind still wins.
2. **Is "body" a new number, or is the old hidden hit-point number renamed and reused for it?** Recommendation: reuse it, so there is one deep health number behind the four body parts and nothing to keep in step.
3. **The backburnered meters: switch off, fold in, or retire?** Recommendation: keep the comeback (the hurt fighter hits harder) as a rule for every fighter inside the new model, set every other meter effect to zero in data now, and remove the code after Alpha.
