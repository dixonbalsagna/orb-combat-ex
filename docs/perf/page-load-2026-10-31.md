# The first load of Orb's private page, phase by phase (Performance and Platform, 2026-10-31)

For the EP, who sat on "Preparing the graphics" for 40 s and more on `http://127.0.0.1:8766/index.html?planet=7&meteor=loud&tiles=1` (`tools/preview/stack-preview.mjs`). Target accepted by the EP: **warm under 10 s, cold about 20 s** (under 10 s cold is not reachable by tuning alone).

## Method

Headless Chrome through Tools' guarded launcher (`tools/machine/browser.mjs`), RTX 5070 Ti (ANGLE Direct3D 11), 1920 by 1080, below-normal priority, a fresh profile per run: **load 1 is a cold first visit** (empty HTTP cache, empty ANGLE shader cache), **load 2 is the same page again in the same browser (warm)**. Page served from this PC, so the download is not a network figure. `docs/perf/tools/load-probe.mjs` records, in the page's clock: long tasks, a frame heartbeat, every WebGL call that can block (program link, uploads, draws) with a tag per program, and, from outside the page, the browser's renderer and GPU process CPU seconds every 250 ms and the machine's busy share (`load-report.mjs` prints it). The CPU seconds are why load does not void the numbers: during the shader compile the renderer's CPU is about 0.1 s per 2 s while the GPU process uses 2 to 3 s per 2 s, so the main thread is waiting on the compile, not starved; during the planet load the renderer's CPU equals wall time (2.0 s per 2 s), so it ran flat out. **The machine was 77 to 90% busy from other sessions' captures throughout**; the figures are as measured, the CPU shares are the check.

The game's own marks come from a scratch copy of the same stack with `docs/perf/tools/scratch-hooks/hook-loadmarks.mjs` (marks and per-step totals in `main.gd`; nothing in the repo changes). Two stacks were measured: the stack Orb's page had at the first capture (**with** Simulation's `architecture-field-frame`, so the tile ground is built, `tiles=1`), and the stack the manifest builds now with field-frame left out as "unreviewed" (**no** tile ground). Both on d5a0924f's main.

## The table (seconds from the page's start; field-frame + tile ground = Orb's page)

| Phase | Cold | Warm | What it is, and the check |
|---|---|---|---|
| Download (wasm 39.5 MB, pck 9.7 MB, js) and wasm compile | 0.3 + 0.2 | 0.2 + 0.1 | localhost; the compiled wasm is cached in warm |
| Engine up (to the first autoload) | 3.1 | 0.8 | cold holds two Godot default programs, 1.9 s of link wait, the start block's longest freeze 2.5 to 2.9 s |
| Scripts (the boot entry loads the graphs a frame each) to `main._ready` | 3.5 | 3.4 | GDScript compile in wasm; no freeze over 0.1 s |
| **Sim planet load** (the loading line, a slice a frame) | **11.3** | **11.3** | timed work 7.1 s; 573 slices; CPU = wall |
| **Pane build** (the match's panes in 30 ms steps) | **2.5** | **2.1** | tile build 1.2 s, ground meshes 0.5, the rest 0.4 |
| **Shader warm-up** (178 programs) | **28.8** | **2.3** | cold: the main thread waits on the driver |
| **To the card (boot done)** | **49.9** (46.8 in the first capture) | **20.3** (20.6) | |

Without the tile ground (the stack as the manifest builds it now): cold 26.6 s, warm 15.5 s; 117 programs, 8.6 s cold compile, 1.1 s warm, no pane-build phase. **So the tile ground costs about +23 s cold and +4.8 s warm.**

## Inside the sim planet load (11.3 s)

| Step (`SimHost.load_step`) | Slices | Total | Longest slice |
|---|---|---|---|
| `ring` (World's gen 3 field) | 318 | **4.5 s** | **0.85 s** (a freeze) |
| `places` | 169 | 1.5 s | 19 ms |
| `climate` | 79 | 0.7 s | 15 ms |
| `match` (the match's own pieces) | 7 | 0.35 s | 0.25 s |

The timed work is 7.1 s; the other 4.2 s is the frames around it (573 slices, one a frame, about 7 ms of engine, draw and browser per frame). The slice is a fixed number of units (`SimRun.planetUnitsPerRead`, "about 5 ms"), which on wasm is 12 ms, so the load takes as many frames as units and does not use the frame.

## The pane build (2.1 to 2.5 s, tile ground on)

`_bs_tiles` 1.17 s (93 steps), `_bs_meshes` 0.5 s, `_bs_fighter` 0.1 s (two), `_bs_share` 0.09, `_bs_refresh` 0.08, `_mb_attach` 0.07, `_bs_materials` 0.05, `_mb_picture` **0.03 s**. **The pose bake is not a cost here**: the first picture is 34 ms (Animation's incremental bake already moved it).

## The shader warm-up (what the cold 28.8 s is)

354 `getProgramParameter` calls for 178 programs: 27.6 to 29.0 s of link wait cold, 0.3 s warm. Uploads, draws and texture calls together are under 1.5 s. Five families of programs, **all of them only with the tile ground**, are 14.9 s of it: vertex/fragment sizes 44k/128k chars (6 programs, 4.4 s, the slowest single ones 1.2 s each), 55k/106k (6, 3.6 s), 51k/96k (5, 2.9 s), 56k/106k (5, 2.3 s), 54k/100k (4, 1.7 s). The other 61 programs the tile ground adds make up the +19.3 s. Rendering's `docs/rendering/boot.md` explains that four of the six programs of a material are Godot's default specializations the game never draws, so most of these are never drawn. Freezes cold (main thread blocked, line still up): 4.6, 3.7, 3.3, 2.9, 2.3 s, all in this phase; warm: none over 0.9 s.

## The two cuts, and what else (owners)

1. **The tile ground's shaders: about -19 s cold** (Rendering). Five big program families that the plain ground does not have; the stack without the tile ground compiles 117 programs in 8.6 s. Make the tile materials share one terrain program with the plain ground's size, or cut the code size of `ground_vertex`'s tile path as the boot park did before; and every tile material variant costs six programs, so fewer materials is fewer programs. The engine-side fix (a custom web template that skips Godot's four default specializations per material and uses `KHR_parallel_shader_compile`) is Tools' and would help every shader, but is a larger job. The browser keeps the compiled programs, so only a first visit or a changed shader source pays.
2. **The sim planet load, 11.3 s in both visits, and the main reason warm is 20 s** (Simulation for the pacing, World for the field). (a) Pace by time: run slices until about 12 to 16 ms of the frame has gone, or two to three a frame, while the loading line is up: 573 frames of 7 ms overhead become about 200: **about -2.5 to -3 s** (an estimate; it needs a run). (b) `ring` is 4.5 s and one slice is 0.85 s: World's gen 3 field cost, with `places` and `climate` another 2.2 s: an algorithmic cut is World's call. (c) A made planet is a deterministic function of its seed, so a second visit of the same planet could read it back from the browser's storage (a hash check keeps it equal to the generated one): **about -7 s warm**, which with (a) is the way to **warm under 10 s** (20.3 - 10 = about 10). That is Simulation's design call and a determinism risk to gate.
3. The start block, 3.5 s of script load plus 0.8 s of engine start, is the same in warm; Tools' (the compiled-script cost; a smaller graph is Simulation's, `load-split.md`).

Where it lands if 1 and 2 both come off: warm about 10 s, cold about 10 + the plain ground's 8.6 s compile = **about 19 s**, which is the EP's target.

## Limits

One machine (RTX, headless Chrome, not Opera: the same Chromium engine, a different cache policy is possible); one planet and seed; two cold captures (46.8 and 49.9 s, on slightly different stacks), one warm each side; the machine 77 to 90% busy, so absolute times are as measured under that load (the renderer CPU matched wall in the planet load; the GPU process CPU matched in the compile, so neither was starved). The breadcrumb stage names did not report in the plain preview export, so the phase edges come from the hook's marks (the hook adds a handful of marks and per-step sums, under 1 ms). "Warm" assumes the browser's cache survives; Opera was not run. The savings in 2(a) and 2(c) are estimates, not runs.
